Architecture · Pi

How Pi's extensibility works

Pi is not a coding agent with a plugin API bolted on — it's an inversion-of-control framework where a minimal core defers nearly every behavioral decision to files in standard directories. Here is the system in one read.

In one paragraph Lifecycle, end to end Event pipeline Tool registry Resource discovery System prompt Session tree TUI surfaces Self-modification Stale-object guards The web-ui split Lessons for self-modifying software

The whole idea in one paragraph

A Pi turn is a pipeline, not a function call. Before the LLM runs, before a tool executes, before a response is rendered — the core pauses and asks the extension chain "anyone want to change this?" Extensions are TypeScript files in ~/.pi/agent/extensions/ that subscribe to lifecycle events. Each handler returns a value that flows into the next handler, so behavior composes like middleware. The core has no subagents, no plan mode, no permissions UI — those are all extensions. Because everything is a file Pi's own read/write tools can touch, Pi can extend itself at runtime via /reload.

  • 7 customization axes compose orthogonally: extensions, tools, resources, prompt, sessions, TUI, providers.
  • 29 event hooks span the full agent lifecycle with chained return values (middleware, not pub/sub).
  • Files, not config: extensions, skills, prompts, themes, settings — all standard directories the agent's own tools can edit.
  • Hot reload: /reload rebinds everything without dropping the session. Stale-object guards (assertActive) catch the subtle bugs this introduces.
  • Tree-structured sessions make modification reversible — try a change, fork if it breaks, navigate back.

01The lifecycle, end-to-end

Where extensions can plug in across a single user turn.

Each moss-outlined box is an extension hook. Handlers chain — handler N+1 sees handler N's output.

02The event pipeline: middleware with backpressure

29 events, all chained, most with structured return values.

What separates Pi's events from a typical pub/sub plugin system: they're not fire-and-forget. Each handler returns data that the next handler sees and can transform. This is the Observer pattern applied as a pipeline.

The four most powerful event types

EventWhat it can doReal-world use
tool_call Mutate event.input in place; return { block: true, reason } to cancel. Permission gates that rewrite dangerous paths.
context Receives a deep copy of all messages before each LLM call. Filter, inject, or rewrite. Result chains. Inject memory snippets; redact secrets.
before_agent_start Return { systemPrompt } to rewrite the prompt per-turn. Each handler sees the accumulated result. Plan-mode injects [PLAN MODE ACTIVE] instructions.
input { action: "transform" } rewrites, "handled" short-circuits the LLM, "continue" passes through. /ping returns "pong" without an API call.
Code · a tool_call gate
export default function myExtension(api) {
  api.on("tool_call", (event) => {
    if (event.toolName === "bash" && event.input.command.includes("rm -rf")) {
      return { block: true, reason: "destructive command blocked" };
    }
    // Rewrite arguments in place — no re-validation needed
    if (event.toolName === "read") {
      event.input.path = sanitize(event.input.path);
    }
  });
}

03The unified tool registry

Built-in tools and extension tools are the same thing.

Pi's built-ins (read, bash, edit, write, grep, find, ls) are just ToolDefinition objects in the same registry as extension tools. The dispatch layer has zero special-casing.

Code · registering a tool
api.registerTool({
  name: "weather",
  description: "Get current weather for a city.",
  promptSnippet: "weather: city → temp/conditions",
  input: Type.Object({ city: Type.String() }),
  async execute(input) {
    return await fetchWeather(input.city);
  },
  renderResult(result) {
    // Custom TUI rendering — Pi defers display to you
    return [`☀ ${result.temp}°`];
  }
});
Why this matters
Extensions can replace built-in tools by registering with the same name. The setActiveTools() API toggles tools at runtime. tool_call/tool_result hooks are installed once on the Agent and delegate via the current runner — so /reload swaps the runner without re-wiring hooks.

04Resource discovery: file-based everything

No registry, no UI config. Drop a file in the right place.

Pi auto-discovers resources from global (~/.pi/agent/), project (.pi/), package (package.json pi.* fields), and CLI sources. Project overrides global; CLI overrides both. Every loaded resource carries SourceInfo provenance.

Pi collects every AGENTS.md/CLAUDE.md from cwd up to the git root. A monorepo gets root-level conventions and per-package overrides, layered automatically.

Skills follow a public standard

Skills implement the Agent Skills spec. Discovered, validated, rendered as XML in the prompt. Skills with disable-model-invocation: true stay invisible to the LLM but remain callable via /skill:name.

05The system prompt is composed, not static

Assembled at runtime from eight pluggable pieces.

The BuildSystemPromptOptions struct holds all structured inputs. Extensions receive it in before_agent_start.event.systemPromptOptions so they can inspect what Pi loaded without re-parsing — and then return a new systemPrompt for that turn.

06Sessions are a tree, not a log

Branching and forking enable safe self-modification.

Sessions are JSONL files where each entry has id and parentId. This isn't cosmetic — it's the safety mechanism for self-modification.

/fork — new file

Creates a new session file from any point. Original preserved on disk.

/tree — same file

Branch in place. Abandoned branches get auto-summarized so context survives.

Compaction is additive

Old messages are summarized into a CompactionEntry — but never deleted from the JSONL.

Extension state lives here too

pi.appendEntry("my-type", data) writes custom entries that aren't sent to the LLM. Restore on session_start.

07The TUI is a component tree, not a fixed UI

Extensions can replace the editor, footer, header, or whole panels.

All components implement a simple interface: render(width) returns string[], optional handleInput(data), optional Focusable for cursor positioning. Components compose via Container.addChild(). Themes hot-reload via component invalidate().

08The self-modification loop

Pi can extend itself because everything is a file its own tools can edit.

Why this actually works

  1. Extensions are .ts files loaded via jiti — no compile step, full Node API.
  2. Skills are Markdown. Drop a SKILL.md in ~/.pi/agent/skills/ and it's instantly available.
  3. Prompts, themes, settings — all files. The agent's own read/write/edit tools manipulate them.
  4. /reload re-runs resource discovery, reloads extensions, rebinds the runner. Session preserved.
  5. pi.registerProvider() lets extensions add LLM providers (custom models, OAuth, streaming) at runtime.
  6. pi.sendUserMessage() + delivery timing ("steer", "followUp", "nextTurn") lets extensions orchestrate multi-step workflows.
  7. Session-replacement APIs (ctx.newSession(), ctx.fork(), ctx.switchSession()) with assertActive() guards prevent stale-object bugs.
The net effect
Pi is a framework for building coding agents, not a coding agent with a plugin API. The author moved every behavioral decision out of the core and into extension points — and because those extension points are just files the agent's own tools can touch, Pi can meaningfully participate in extending itself.

09The hard part: stale references after reload

Self-modification introduces a class of bugs that don't exist in static systems.

Hot reload is the feature that makes self-modification useful. It's also the feature that introduces the subtlest bug class in the whole system. Pi solves it with two related patterns — runner indirection and explicit invalidation — that are worth stealing.

The bug class: time-of-check vs. time-of-use

Imagine extension A captures a ctx object in a closure (say, a command handler). The user runs /reload, which swaps the extension runner. Now the closure fires and dereferences ctx — but the runner that object pointed to is gone. Without guards, you get silently wrong behavior: messages sent to a dead session, providers registered against a vanished registry, tool calls vanishing into the void.

The two patterns

Pattern 1 · runner indirection

The tool hooks (beforeToolCall, afterToolCall) are installed once on the Agent. They read this._extensionRunner at call time. So /reload swaps the runner pointer; the hooks themselves never need rewiring.

Pattern 2 · explicit invalidation

Each extension instance carries an ExtensionRuntimeState. On teardown, invalidate(reason) is called. Any subsequent ctx.assertActive() throws a developer-facing message explaining what to do instead.

Code · the error message that teaches
// Pi's actual invalidation message — the message itself is the docs:
"Do not use a captured pi or command ctx after ctx.newSession(),
 ctx.fork(), ctx.switchSession(), or ctx.reload(). For newSession,
 fork, and switchSession, move post-replacement work into withSession.
 For reload, do not use the old ctx after await ctx.reload()."
Why this matters
Static systems can't have this bug. Self-modifying systems get it for free. If you build one, you need both: a stable indirection (so external callers don't shatter when internals swap) and an explicit fail-fast (so internal callers can't silently operate on dead state).

10The web-ui split: same core, different extensibility model

Not every consumer should get the full extension API. Pi's solution is interesting.

Pi recently grew a packages/web-ui sibling to the CLI. It reuses the same pi-ai and pi-agent-core packages that power the terminal agent, but exposes a different extensibility surface — and that's the lesson worth studying.

Two extensibility models, one engine

The design insight
A self-modifying agent doesn't want to ship its full reflection API to every embedder. The CLI gets the reflective surface — because that's where the agent runs as a peer of the user. The web-ui gets a tight component contract — because that's where third parties want stability. Same engine underneath; different extension shapes per audience.

11Lessons for building self-modifying software

Generalizable principles, pulled out of Pi's specific implementation.

If you take Pi apart, the load-bearing decisions aren't really about agents or LLMs. They're patterns for any system that needs to safely modify itself at runtime. Here's what to steal.

1 · Pick a substrate the system can already read and write

Pi extensions are .ts files. Skills are .md. Themes are .json. The agent has read, write, and edit tools. That's not a coincidence — it's the whole game. A self-modifying system needs its modification surface to be the same thing it operates on. If your config lives in a database with a custom admin UI, your agent can't change it without first being taught what the admin UI is.

Generalization: if you want X to be self-modifiable, X has to live in the medium the modifier already understands. Files for code agents. SQL rows for SQL-speaking agents. HTTP endpoints for browser agents. Match the substrate to the actor.

2 · Pipelines beat buses when behavior must compose

Pi's 29 events are middleware, not pub/sub. Each handler receives a payload, can mutate or replace it, and returns it to the next handler. Pub/sub gives you observation but not composition — three plugins listening to tool_call can't all rewrite the args, because there's no defined merge.

Generalization: if extensions need to collaborate on a decision (block, transform, augment), use a pipeline with structured return values and a defined order. If they just need to observe (log, metric, audit), pub/sub is fine. Most interesting extensibility points are the first kind.

3 · Stable indirection + explicit invalidation = safe swaps

Pi installs hooks on the Agent once. Those hooks dereference this._extensionRunner at call time. So /reload swaps the runner pointer; nothing else changes. This is the "stable indirection" half. The other half is assertActive() — old objects fail loudly the moment anyone tries to use them after invalidation.

Generalization: any system with hot-swappable internals needs a stable seam (a pointer the outside world holds, that internally redirects to the current implementation) and a fail-fast contract (so captured references can't silently operate on dead state). The bug class you're avoiding is silent misbehavior; the cure is loud crashes at the boundary.

4 · Make rollback first-class via tree history

Pi sessions are id/parentId trees, not linear logs. The agent can fork before a risky modification, try it, and navigate back if it goes wrong. Compaction is additive — old messages get summarized, but never deleted.

Generalization: any system that modifies itself must have a "back" button at the granularity of the modification. Git models this for code. Pi models it for conversational state. Without it, self-modification is one-way and therefore unsafe.

5 · Track provenance from day one

Pi tags every resource with SourceInfo — source (builtin/local/npm/git/cli/sdk), scope (user/project/temporary), and baseDir. When the agent generates an extension, it can later inspect what it created vs. what was already there. Provenance is what lets a self-modifying system audit itself.

Generalization: if your system can be modified by multiple actors (humans, agents, packages, CLI flags), every artifact needs a "who/where/when" tag. Without it, the agent can't reason about what's safe to change.

6 · Defer every decision the core doesn't have to make

Pi's core has no subagents, no plan mode, no permission UI, no MCP, no background bash, no todos. All of those are extensions. The core provides the seam; extensions provide the policy. This isn't minimalism for its own sake — it's that every decision baked into the core is one the agent can't change about itself.

Generalization: for any feature, ask "must this be in the core, or can it be expressed in terms of core primitives?" If it can be expressed via the extension API, ship it as an extension — even if you write the extension yourself. That way users (and the agent) can replace it without forking.

7 · Match the extension surface to the trust boundary

The CLI gets the full reflective API because it runs locally with full Node access — the user (and the agent) already have the keys. The web-ui package, which runs in browsers and gets embedded into hosted apps, exposes only props and component slots. Same engine, deliberately different surface.

Generalization: a self-modifying system probably needs two extension APIs — a wide one for the trusted edge (where the actor is a peer of the maintainer) and a narrow one for the untrusted edge (where third parties build on top). Don't ship the reflective surface to the untrusted side.

8 · Progressive disclosure for AI consumers

Pi puts short descriptions of skills in the system prompt; the LLM reads the full skill on demand via read. Tool snippets are one-liners. The LLM never sees the full tool schema upfront — just enough to know what exists and when to call it.

Generalization: when an LLM is one of your extension consumers, treat its context window as the constraint. Index everything with one-line summaries; let the model pull detail on demand. This is the same shape as a good README — purpose at the top, depth on click.

The meta-pattern
Self-modifying software isn't a single technique. It's the composition of seven smaller decisions, each individually defensible: file-based substrate, pipeline middleware, stable indirection, tree history, provenance, deferred decisions, audience-shaped surface. Drop any one and the others stop being safe.

Reading this once should give you the mental model. To go deeper: start with extensibility.md, then read an existing extension in ~/.pi/agent/extensions/ alongside the ExtensionAPI type definitions.
